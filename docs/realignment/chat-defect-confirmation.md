- Active contract/BFF/frontend/Gateway source files checked on 2026-05-12

## Decision Rule

Treat a candidate as a Phase 5 defect only when it affects the active chat
control surface and has evidence in the current contract chain:

```
Gateway protocol/runtime truth
  -> deck-go contracts/product truth
  -> generated TS/Go artifacts
  -> Go BFF adapter/routes
  -> frontend API/store/view model
  -> stream/readback verification
```

Historical remediation files, old planning artifacts, and unused compatibility
types are not defects by themselves.

## Recommended Confirmation Set

My recommendation is:

- Confirm **C1** as a real Phase 5 defect to fix.
- Confirm **C2** as a real Phase 5 defect if compaction remains part of the
  active chat maintenance surface.
- Confirm **C3** as a Phase 5 verification item before deciding whether the fix
  belongs in code or contract metadata.
- Keep **C4-C9** out of the first implementation pass unless the Phase 5 trace
  proves active impact.

This keeps Phase 5 focused on active chat reference defects while avoiding a
repository-wide cleanup of historical artifacts.

## Phase 5 Stop Condition

Implementation must not start until the user confirms this table. If the user
accepts the recommended confirmation set, the next plan should cover:

1. product contract metadata repair for C1;
2. compaction response contract alignment for C2 if confirmed;
3. stream cursor/gap verification for C3;
4. contract generation and narrow verification gates;
5. final chat reference trace evidence.
