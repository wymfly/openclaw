## 1. 权限模型实用性分析

### 1.1 "空间内互信"模型 vs 制造业数据敏感性

设计文档提出"空间内所有 Agent 互信，共享空间资源"。这在制造业场景下存在**适用性缺口**：

| 数据类型                       | 保密等级 | 空间互信是否适用 | 风险                                   |
| ------------------------------ | -------- | ---------------- | -------------------------------------- |
| 工艺参数（激光功率、扫描策略） | 核心机密 | ⚠️ 需分层        | 同空间的质量工程师不应看到全部工艺配方 |
| 材料配方                       | 核心机密 | ⚠️ 需分层        | 材料供应商信息可能涉及商业秘密         |
| 质量检测数据                   | 内部保密 | ✅ 基本适用      | 同部门可共享，但客户项目数据需隔离     |
| 设备日志                       | 内部一般 | ✅ 适用          | 可能包含产能信息但风险可控             |
| 生产排程                       | 内部保密 | ⚠️ 需分层        | 产能信息对竞争对手有价值               |

**核心矛盾**：制造业的"部门"不等于"数据信任边界"。工艺部 3 个工程师可能各自负责不同客户的专有工艺，彼此之间也不应完全互通。

### 1.2 当前设计如何处理细粒度权限？

当前设计的权限控制点：

1. **平台层**：管理员决定哪些资源挂载到空间（卷挂载 rw/ro）
2. **空间层**：容器隔离，不同空间物理隔离
3. **Agent 层**：Agent 权限 ≤ 创建者的平台权限

**缺口**：空间内部没有权限分层。一旦数据挂载到空间，空间内所有用户的所有 Agent 都能访问。

### 1.3 建议：混合模型（空间互信 + 资源分级）

对 20-50 人制造业团队，**不建议**走传统 RBAC（过于复杂，管理成本高），也**不建议**纯空间互信（安全不足）。推荐**混合模型**：

```
空间级信任（主要机制）
  └── 按业务域划分空间，空间间物理隔离
  └── 大部分日常场景靠空间边界就够了

资源级标签（补充机制，阶段2引入）
  └── 资源标记密级：public / internal / confidential / restricted
  └── 配置到空间时可指定密级上限
  └── confidential+ 资源仅对空间内指定角色可见
  └── 实现：在 OpenClaw 实例内通过 Agent skill 白名单 + 工具访问控制
```

**为什么不用传统 RBAC**：

- 20-50 人团队，角色矩阵维护成本太高
- 制造业 IT 人力有限，复杂权限模型会被绕过或荒废
- 空间隔离已经覆盖 80% 场景

**为什么不纯空间互信**：

- 工艺参数是真正的核心资产，不能因为"在同一个空间"就全部暴露
- 合规要求（如 ITAR、客户 NDA）可能要求数据访问可审计

### 1.4 阶段化建议

| 阶段          | 权限模型                | 适用场景                              |
| ------------- | ----------------------- | ------------------------------------- |
| MVP           | 纯空间隔离              | 空间按部门/项目划分，足够覆盖初期需求 |
| 阶段2         | 空间隔离 + 资源密级标签 | 应对客户专有数据、核心工艺参数        |
| 阶段3（按需） | + 审计日志 + 合规报告   | 应对 ITAR/NDA 等合规要求              |

## 2. 用户旅程分析

### 2.1 完整用户旅程：工艺工程师使用 AI 助手

```
Step 1: 打开企业微信（日常入口）
  │
Step 2: 进入"AI 助手"应用号（企微自建应用）
  │      └── 首次使用：看到欢迎消息 + 简单引导
  │      └── 日常使用：直接输入消息
  │
Step 3: 输入问题，如"SLM 316L 的最佳激光功率参数"
  │
Step 4: [平台网关] 企微 webhook → 识别用户 → 查路由表
  │      └── 有 activeAgent → 直接转发
  │      └── 无 activeAgent → 转发到默认 Agent
  │
Step 5: [OpenClaw 实例] 收到消息 → Agent 处理
  │      └── 查知识库 → 调用工具 → 生成回复
  │
Step 6: [平台网关] 收到回复 → 企微 API 回调
  │
Step 7: 工艺工程师在企微看到回复
  │
总耗时预期：2-8 秒（取决于 LLM 处理时间）
```

### 2.2 /switch 交互直观性评估

**问题**：非 IT 人员对"命令行式"交互（`/switch 工艺助手`）接受度低。

**用户测试预测**：

- 工艺工程师（35-50 岁为主）：❌ 不习惯斜杠命令，容易忘记
- 质量工程师（有 ERP 经验）：⚠️ 勉强可学，但不会主动使用
- 设备操作员（一线工人）：❌ 完全不适用

**建议改进**：

| 方案         | 描述                                              | 优先级 |
| ------------ | ------------------------------------------------- | ------ |
| 菜单式切换   | 企微底部菜单栏直接列出 Agent 列表，点击切换       | P0     |
| 关键词触发   | "切换到工艺助手" 自然语言触发，网关层做意图识别   | P1     |
| 保留 /switch | 作为高级用户快捷方式，但不作为主推交互            | P2     |
| Agent 卡片   | 输入 "帮助" 返回可视化 Agent 卡片列表，点击即切换 | P1     |

### 2.3 多 Agent 发现性："我该找哪个 Agent？"

这是**最大的用户体验瓶颈**。制造业员工不会主动探索，需要平台主动引导：

**推荐方案——Agent 目录 + 智能路由**：

1. **Agent 目录页**（企微应用内 H5 页面）
   - 分类展示：工艺类 / 质量类 / 设备类 / 通用类
   - 每个 Agent 一句话描述 + 擅长场景
   - 点击直接开始对话

2. **智能路由（阶段2）**
   - 用户直接提问，网关层根据问题内容自动路由到最合适的 Agent
   - 示例："这批粉末的粒度分布报告" → 自动路由到质量助手
   - 降低用户认知负担，是终极方案

3. **首次使用引导**
   - 注册后推送"你的 AI 助手已就绪"卡片
   - 展示 3 个推荐 Agent + 示例问题
   - "试试问我：XXX"

### 2.4 消息延迟分析

```
企微 webhook 接收      ~100-300ms（企微服务器到平台）
平台网关路由决策       ~10-50ms（内存查表）
WebSocket 转发        ~5-20ms（内网）
OpenClaw Agent 处理    ~2-15s（LLM 推理为主）
回复回传              ~5-20ms（WebSocket）
企微 API 发送回复      ~100-500ms（调企微 API）
────────────────────────────────────
总计                   ~2.5-16s
```

**瓶颈在 LLM 推理**，网关链条本身增加的延迟 < 500ms，可接受。

**关键优化**：

- 平台网关应在收到用户消息后**立即回复"正在思考…"**（企微支持临时回复），避免用户等待焦虑
- 长回复考虑分段发送（企微单条消息限 2048 字符）
- 超时处理：15 秒无回复返回"处理中，稍后回复"

**对 architect 的技术要求**：

- 网关层路由决策必须 < 100ms（纯内存操作）
- WebSocket 连接池需要心跳 + 自动重连，否则消息丢失
- 企微 webhook 必须在 5 秒内响应 200，否则企微会重试（导致重复消息）

## 3. 空间使用模式预测

### 3.1 个人空间 vs 协作空间使用比例

**预测：70% 交互发生在协作空间，30% 在个人空间。**

理由：

- 制造业工作以**团队协作**为主，工艺开发、质量管控都是跨角色协作
- 个人空间的价值主要是"个人笔记 / 通用问答 / 翻译"等轻量场景
- 核心业务数据（工艺库、质量数据、设备日志）都在协作空间
- 员工不会花时间配置个人空间的专业工具

### 3.2 员工电脑模式可靠性评估

**结论：不推荐作为主要模式，只作为 IT/开发人员的可选项。**

| 问题                          | 影响 | 缓解                                  |
| ----------------------------- | ---- | ------------------------------------- |
| 电脑关机 → Agent 不可用       | 高   | 用户不理解为什么"下班后 Agent 不回复" |
| 网络不稳定（工厂环境）        | 中   | 丢消息、延迟高                        |
| 多设备（办公室 + 车间笔记本） | 中   | 状态不同步                            |
| IT 无法统一管理               | 高   | 安全策略无法执行                      |
| 系统更新 / 崩溃               | 中   | Agent 不可预期中断                    |

**建议**：

- 默认所有用户使用**容器模式个人空间**（服务器托管）
- 员工电脑模式仅开放给 IT 人员 / 开发者，作为"高级模式"
- 文档中标注"员工电脑模式不保证可用性"

### 3.3 20 人团队空间规划

**推荐 3-4 个协作空间**：

| 空间名               | 成员                                  | 挂载资源                             | 理由                     |
| -------------------- | ------------------------------------- | ------------------------------------ | ------------------------ |
| 工艺协作空间         | 工艺工程师 3-5 人 + 材料工程师 1-2 人 | 工艺参数库、材料数据库、设备日志(ro) | 核心工艺开发，数据最敏感 |
| 质量协作空间         | 质量工程师 2-3 人 + 检测员 2-3 人     | 质量数据库、检测报告、标准文档       | 质量管控相对独立         |
| 生产协作空间         | 生产主管 1-2 人 + 设备操作员 3-5 人   | 排程系统(ro)、设备日志、操作手册     | 一线生产支持             |
| 管理协作空间（可选） | 部门主管 2-3 人                       | 汇总数据(ro)、KPI 仪表板             | 管理层跨域查看           |

**划分依据**：

1. **数据信任边界**：工艺参数 vs 质量数据 vs 生产数据，天然分离
2. **协作关系**：日常高频协作的人放在一个空间
3. **管理简便**：空间数不超过 5 个，管理员可维护

## 4. 管理员负担评估

### 4.1 创建协作空间步骤分析

```
Step 1: 命名空间 + 选择类型                    [无技术要求]
Step 2: 配置资源——挂载数据卷                   [需要知道数据存放路径]
Step 3: 配置资源——开通 API 访问               [需要知道内部系统端点]
Step 4: 配置 Agent 预装技能                     [需要理解 Agent 能力]
Step 5: 启动容器                                [需要 Docker 基础知识]
Step 6: 添加成员                                [无技术要求]
Step 7: 验证空间可用                            [基本操作]
```

**知识门槛评估**：

- Step 2-3 需要 IT 运维知识（了解数据卷路径、API 端点）
- Step 4 需要业务知识（哪些技能适合哪个空间）
- Step 5 需要 Docker 知识

**现实问题**：制造业的"管理员"通常是 IT 运维（1-2 人），他们可能有 Docker 知识，但缺乏业务理解。配置资源需要 IT + 业务主管协作。

**建议**：

- 提供**空间模板**（工艺空间模板 / 质量空间模板 / 生产空间模板）
- 模板预配置常用资源和技能，管理员只需调整成员和数据路径
- 阶段1 用 CLI 配置可接受（IT 人员操作），阶段2 必须有 Web UI

### 4.2 日常运维频率预估

| 操作                   | 频率                        | 复杂度 |
| ---------------------- | --------------------------- | ------ |
| 加人/减人              | 每月 1-2 次                 | 低     |
| 更新 Agent 配置        | 每周 1-2 次（初期频繁调参） | 中     |
| 调整资源挂载           | 每季度 1-2 次               | 中     |
| 空间创建/销毁          | 每半年 1-2 次               | 高     |
| 处理异常（容器崩溃等） | 不可预测                    | 高     |

**结论**：日常运维负担可控，但**初期（前 2 个月）配置频率高**，需要 IT + 业务紧密配合。

### 4.3 自助化空间

| 自助项                     | 建议                            | 阶段  |
| -------------------------- | ------------------------------- | ----- |
| 用户自己创建个人空间 Agent | ✅ 应该自助                     | MVP   |
| 用户修改 Agent 配置        | ✅ 应该自助（在空间资源范围内） | MVP   |
| 用户创建协作空间           | ❌ 不建议（资源管控需要管理员） | —     |
| 用户邀请他人进入协作空间   | ⚠️ 可考虑"空间管理员"角色委托   | 阶段2 |

## 5. 竞品参考分析

### 5.1 Microsoft Copilot Studio

**权限管理**：

- 基于 Microsoft Entra ID（Azure AD）的 RBAC 体系
- 环境（Environment）级别的安全角色分配，通过组团队（Group Teams）批量管理
- Agent 级别区分 Owner / Editor / Viewer 三种角色
- 集成 Microsoft Purview 实现端到端审计
- 数据策略（DLP）控制 Agent 可访问的连接器

**借鉴点**：

- ✅ "环境"概念类似我们的"空间"，按业务域隔离
- ✅ 通过 Entra ID 组来简化权限管理（对应我们用企微部门）
- ✅ Agent 级别的角色控制（Owner/Editor/Viewer）值得参考
- ⚠️ 整体体系过于复杂，不适合 20-50 人团队直接搬

**来源**：[Microsoft Copilot Studio Security and Governance](https://learn.microsoft.com/en-us/microsoft-copilot-studio/security-and-governance)

### 5.2 Coze（扣子）

**权限管理**：

- 团队版提供协作 + 权限管理 + 数据分析面板
- 企业版支持 SSO 集成 + 私有化部署
- "空间"（Space）概念已于 2025 年推出，定位为"人与 AI 智能体协作的工作空间"
- 按人头收费（团队版 100 人上限，企业版无限）
- 基础版与专业版账号不互通（绑定火山引擎）

**借鉴点**：

- ✅ 空间概念与我们设计高度一致，验证了空间模型的可行性
- ✅ 零代码 Agent 创建降低门槛
- ✅ 插件市场 + 工作流市场生态化
- ⚠️ Coze 面向通用场景，缺乏制造业垂直能力
- ✅ "扣子空间"支持 MCP 协议，与我们的技术路线一致

**来源**：[扣子空间 - AIGC 工具导航](https://www.aigc.cn/space-coze-cn)、[Coze 收费方案分析](https://www.woshipm.com/share/6085470.html)

### 5.3 百度千帆 AppBuilder

**权限管理**：

- 提供细粒度权限管控，精确至文档、数据表的读写级别
- 私有化版额外增强了企业内部权限管理
- 混合云模式：平台私有化 + 调用公有云大模型（保障数据不出域）
- 安全算子：自动屏蔽不良信息输入输出

**借鉴点**：

- ✅ "细粒度到文档级别"的权限控制思路值得空间内资源分级参考
- ✅ 混合云模式与我们的"员工电脑 + 服务器容器"异曲同工
- ✅ 安全算子（内容过滤）可借鉴到 Agent 回复审核
- ✅ 私有化版设计思路与我们高度一致

**来源**：[百度千帆 AppBuilder 产品文档](https://cloud.baidu.com/doc/AppBuilder/s/6lq7s8lli)

### 5.4 行业最佳实践（2025-2026）

根据 ISACA、KPMG、Deloitte 的企业 AI Agent 报告：

- **唯一身份**：每个 Agent 应有独立服务账号，不共用凭证
- **最小权限**：Agent 权限限制在任务所需最小范围
- **零信任**：短期 token + 实时权限验证，尤其对跨系统操作
- **凭证注入**：Agent 不存储凭证，通过服务网格/网关动态注入
- **审计可追溯**：每个 Agent 的决策必须可追溯到数据源 + 时间戳
- **60% 的企业**限制 Agent 访问敏感数据时要求人工监督

**来源**：[ISACA Agentic AI Best Practices](https://www.isaca.org/resources/news-and-trends/industry-news/2025/safeguarding-the-enterprise-ai-evolution-best-practices-for-agentic-ai-workflows)、[KPMG AI Pulse Survey 2026](https://kpmg.com/us/en/media/news/q4-ai-pulse.html)

## 6. 跨角色影响评估（Phase C）

### 6.1 对 architect 的技术要求

| 产品需求                    | 技术要求                                | 优先级 |
| --------------------------- | --------------------------------------- | ------ |
| 消息延迟 < 3 秒（不含 LLM） | 网关路由 < 100ms，WebSocket 心跳 + 重连 | P0     |
| "正在思考…"即时反馈         | 企微 API 临时回复能力，异步消息模型     | P0     |
| 企微 webhook 5 秒内响应     | 异步处理架构，webhook 立即返回 200      | P0     |
| Agent 目录页                | 需要 H5 页面嵌入企微，跨空间 Agent 索引 | P1     |
| 智能路由                    | 网关层意图分类模型或规则引擎            | P2     |
| 空间模板                    | 配置持久化 + 模板 CRUD API              | P1     |

### 6.2 对 domain-expert（企微集成）的影响

- **权限模型简化**（推荐方案）→ 企微集成更简单：用户-空间映射直接用企微部门 API 同步
- **权限模型复杂化**（如引入 RBAC）→ 企微集成需要额外维护角色同步，增加 IT 配置负担
- **建议**：企微部门结构 → 平台空间成员，一键同步，减少手动配置

### 6.3 非 IT 用户学习成本降低方案

**渐进式上手策略**（3 步走）：

```
Week 1：被动体验
  └── 管理员预配置好 Agent
  └── 用户只需在企微发消息，默认路由到适合的 Agent
  └── 零学习成本

Week 2-4：主动探索
  └── 推送"你还可以试试这些"提示
  └── 引导使用 Agent 目录
  └── 学习菜单切换 Agent

Month 2+：高级使用
  └── 自定义个人 Agent
  └── 调整 Agent 参数
  └── 使用 /switch 快捷指令
```

**关键原则**：第一天就能用，不需要任何培训。

## 7. 关键发现摘要

### 高优先级发现

1. **空间互信模型 MVP 阶段够用**，但必须在设计中**预留资源分级扩展点**（阶段2 引入资源密级标签）
2. **/switch 命令对非 IT 用户不友好**，必须提供**菜单式切换**作为主要交互方式
3. **Agent 发现性是最大 UX 瓶颈**，需要 Agent 目录页 + 首次使用引导 + 长期智能路由
4. **员工电脑模式不靠谱**，默认应使用容器模式，员工电脑模式仅作为高级选项
5. **消息延迟可接受**，但必须实现"正在思考…"即时反馈

### 中优先级发现

6. 20 人团队推荐 3-4 个协作空间，按数据信任边界划分
7. 管理员负担可控，但需要**空间模板**降低初始配置成本
8. 企微部门结构应自动同步为空间成员，减少手动维护
9. 竞品验证了"空间"模型的可行性（Coze 空间、Copilot Studio 环境）

### 低优先级 / 远期

10. 智能路由（自动识别问题类型分发到合适 Agent）是终极方案，阶段2+ 考虑
11. RBAC 暂不需要，但审计日志在阶段2 应优先引入
12. 空间管理员角色委托（允许业务主管管理空间成员）在阶段2 考虑
