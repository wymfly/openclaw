# Skill 摘要（由 orchestrator 从完整 Skill 和 CLAUDE.md 提取）

## 项目级质量约束（来自 CLAUDE.md，Codex 不可见，必须遵守）

- 每次修改后运行 `pnpm tsgo 2>&1 | grep "extensions/wecom"` 检查新增 TS 错误
- 编写 API 调用代码前，先读取 doc/client.ts 确认 import 路径和 retry pattern
- mock 对象必须包含所有必填字段（尤其 `callbackConfigured`、`apiConfigured`）
- mock patch 路径 = 消费方的 import 路径（不是定义方的路径）
- `LIMITS` 从 `../../types/constants.js` import（不是 `../../monitor/state.js`）
- `resolveAgentAccountOrUndefined` 从 `../bot/fallback-delivery.js` import
- `getAccessToken` 从 `../../transport/agent-api/core.js` import
- `wecomFetch` 从 `../../http.js` import
- `resolveWecomEgressProxyUrlFromNetwork` 从 `../../config/index.js` import
- Tool 注册 pattern: `api.registerTool((toolContext: any) => ({...}))` — 参考 `doc/tool.ts:360`
- Account 解析 pattern: `params.accountId || toolContext?.accountId || "default"` — 参考 `doc/tool.ts:368`
- 提交使用 `scripts/committer` 或 `--no-verify`（pre-existing TS errors in test files）

## WeCom Extension 架构约束

- 新模块遵循 `capability/doc/` 四件套 pattern: client.ts, schema.ts, tool.ts, types.ts
- 每个 client 内部复制 retry pattern（设计决策 D4，不提取共享函数）
- Schema 使用 oneOf 判别联合，action 字段分发
- Tool 注册函数命名: `registerWecom<Module>Tools`
- 所有 API 请求通过 `wecomFetch` + proxy + timeout

## 测试约束

- vi.mock 放在文件顶层，不放在 describe/it 内部
- 每个 test 文件开头 mock 三件套: getAccessToken, resolveWecomEgressProxyUrlFromNetwork, wecomFetch
- beforeEach 调用 vi.clearAllMocks()
- Mock agent 必须包含: accountId, configured, corpId, corpSecret, agentId, token, encodingAESKey, config, network, callbackConfigured, apiConfigured
