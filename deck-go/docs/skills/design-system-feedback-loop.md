# Skill: Design System Feedback Loop

> **何时启用**：项目已有基线 design system（tokens + atoms + 部分 molecules），开始进入"做新模块 → 反哺系统"的常态化阶段。
>
> **目标**：让 design system 在产品迭代中**有机生长**，既不僵化（阻碍创新）也不抖动（频繁 breaking change）。

---

## 核心理念

> **Design system 是产品，不是法律。**

底层为上层服务，上层有权挑战底层。这不是"违反规则"，是健康协作。

```
契约层（API / Schema）         ← 稳定、慢变、强约束
    ↓
基础设施层（Design System）    ← 中速演进、被反哺
    ↓
产品层（功能模块）              ← 快速迭代、质量优先、可越界
```

三层节奏不同：API 一年改两次、design system 一季度演进一次、模块一周一迭代。

---

## 自由度分层（设计模块时的硬约束）

设计任何新模块前，先在心里把这张表过一遍。

| 层级                | 自由度              | 操作准则                                                                 | 反例                                          |
| ------------------- | ------------------- | ------------------------------------------------------------------------ | --------------------------------------------- |
| **Tokens**          | 🔒 严格遵守         | 颜色/字体/间距/圆角/阴影只能用 `--ds-*` token                            | 不能写 `color: #3a7bff`、不能 `padding: 13px` |
| **Atoms**           | ⚠️ 优先复用，可扩展 | 用现有 Button / Input / Badge；缺 variant 时**走 PR 加 variant**，不重写 | 不能在模块里造一个 `<MyButton>` 重新实现      |
| **Molecules**       | ✅ 自由组合         | 用 atoms 拼新 molecule，**就地写在模块文件夹**，不立即抽象               | 鼓励                                          |
| **页面布局 / 交互** | ✅ 完全自由         | 创新空间在这层                                                           | 鼓励                                          |

**口诀**：底层"借用"，中层"组合"，上层"创造"。

---

## 反哺判断标准

不是所有"就地写的组件"都该回流到 design system。判断它**值不值得反哺**：

### ✅ 值得反哺的迹象（满足任一即可）

1. **同一个模式在 ≥2 个模块出现**——重复是抽象的最强信号
2. **现有 atom/molecule 组合不出来**，且需求合理（不是奇葩需求）
3. **解决了一类共性问题**：性能、可访问性、键盘交互、错误状态
4. **模式本身有"教学价值"**——其他模块看到后会想"原来还能这样"

### ❌ 只是想破坏的迹象（必须忍住）

1. "我觉得这个按钮应该再大点"——**口味问题**，找设计 owner 讨论是否改 token
2. "我想用一个更酷的动画"——**一次性炫技**，留在模块里就好
3. "我懒得查 token，直接写 hex"——**纯偷懒**，PR review 直接打回
4. "这个组件只有我用"——**孤儿组件**，不要污染公共空间

---

## 反哺时机：季度 batch，不要边做边改

**绝对不要**：做新模块时顺手改 design system 主线代码。

**应该这样**：

```
Week 1-12（一个季度）
├─ 模块 A 上线（含就地组件 a1, a2, a3）
├─ 模块 B 上线（含就地组件 b1, b2, b3）
├─ 模块 C 上线（含就地组件 c1, c2, c3）
│
Week 13（季度反哺日）
├─ 召集所有模块 owner 一起 review 就地组件
├─ 标记 ≥2 模块出现的模式 → 候选
├─ 候选组件做接口设计（命名、props、variant）
├─ 抽到 design system，发 v1.x.0
└─ 各模块下个迭代切换到新版本
```

**为什么 batch？**

- 边做边改 → design system 持续抖动 → 模块永远在追新版本 → 信任崩溃
- batch → 一次性升级 → 所有模块同步切换 → 版本节奏稳定

**例外**：tokens 层的紧急修复（颜色对比度不够、间距 token 缺失等基础问题）可以走 hotfix，不必等季度。

---

## 季度反哺 review 的执行流程

每个季度末跑一次，1-2 小时会议 + 后续 PR：

### Step 1：盘点就地组件（reviewer 准备）

review 前，DS owner 用 `grep` / `ripgrep` 在所有模块里找：

- 重复的 className 模式
- 重复的 JSX 结构
- 跨模块出现的 hex 色值、px 值（说明 token 不够用）

输出一份 **"候选列表"**：组件名 + 出现位置 + 重复次数。

### Step 2：会议讨论（30-60 分钟）

每个候选过一遍，三选一：

- 🟢 **Promote**：抽到 design system，下季度切换
- 🟡 **Watch**：再观察一个季度，看是否更稳定
- 🔴 **Reject**：留在模块里就好，不抽

判断时用前面的"反哺判断标准"。

### Step 3：接口设计（DS owner 负责）

被标记 Promote 的组件，**不要直接照搬**就地实现。要重新设计接口：

- 命名：是不是符合 design system 命名规范？
- props 是否最小化？是否容易扩展？
- variant / size / state 三套是否完整？
- 跟现有 atoms/molecules 是否风格一致？

接口设计完，发给三个使用方先 review，**他们点头才能合入**。

### Step 4：实施 + 迁移

- DS owner 实现新组件，更新 `/design-system` review canvas
- 发 changelog（哪些是新增、哪些是 deprecate）
- 各模块在下个迭代切换；deprecate 的旧用法保留 1-2 个版本，给迁移窗口

---

## 命名与版本

- **新增**：minor 版本（v1.2.0 → v1.3.0）
- **修改 props**（兼容）：minor
- **breaking change**：major（v1.x.x → v2.0.0），且**强制写迁移指南**
- **token 调整**：patch（视觉微调）或 minor（新增 token）

每次反哺合入主干，写一份 `CHANGELOG.md` 条目，至少包含：

- 改动摘要
- 影响范围（哪些模块需要切换）
- 迁移路径（从旧用法到新用法的 codemod 或手动步骤）

## 早期项目的特殊情况

如果项目刚起步，design system 还很稀薄：

1. **不要试图用现有 atoms 拼出完整页面**——拼不出来很正常
2. **先设计完整页面，再回头抽组件**——这是最健康的顺序
3. **缺的就地手写**，不立刻抽到 design system
4. **2-3 个页面做完后**，看哪些"就地组件"重复出现，**这时候才抽**
5. 第一个完成度高的页面要变成"风格锚点"，后续页面跟它对照，防风格漂移

> Linear、Vercel 早期都是这样长出来的——先有产品，后有系统。

---

## 文档锚点

每次反哺周期结束后，更新这两份文档：

- `src/design-system/README.md`——加入新组件的使用说明
- `src/design-system/CHANGELOG.md`——记录版本演进

季度结束时把这两份发给团队，让所有人知道 design system 又长大了一圈。

---

## 反模式（千万别做）

- ❌ **每个 PR 都顺手改 design system**——会让 DS 成为永远的瓶颈
- ❌ **一次性把所有"就地组件"全抽走**——大重构，风险极高
- ❌ **跳过接口 review 直接合入**——抽出来的组件接口烂，迁移困难
- ❌ **deprecate 旧用法不给迁移窗口**——逼模块紧急修复，破坏迭代节奏
- ❌ **只看代码不看视觉**——抽出来的组件视觉上不一致，更糟
- ❌ **DS owner 一个人决定**——没有使用方背书的抽象，注定要返工

---

## 一句话总结

**模块自由地创新，季度有节奏地收敛，design system 在产品的真实压力下生长。**
