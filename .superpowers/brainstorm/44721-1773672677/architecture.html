Communication Flow

Browser → Server REST API (Next.js API Routes) for all mutations + queries
Server → Browser SSE for real-time events (chat stream, status updates, notifications)
Server → Gateway WebSocket (OpenClaw Protocol v3, challenge-response auth)
Server → Disk SQLite (deck state) + File I/O (OpenClaw config/sessions read)

Key Design Decisions

Browser never talks to Gateway directly
Server holds the WS connection. Browser only speaks HTTP/SSE to the server. This enables security, caching, and future multi-Gateway support for claw-platform.
SQLite for deck state only
OpenClaw's own data stays in ~/.openclaw/. SQLite stores dashboard-specific state: event outbox, usage aggregation, budget rules, webhook config.
EventBus bridges WS → SSE
Gateway events arrive via WS, get processed + persisted, then broadcast to all browser clients via SSE through an in-process EventBus.
API Routes as platform contract
Every API Route is a clean interface. claw-platform can later wrap, extend, or proxy these routes without touching the deck internals.
