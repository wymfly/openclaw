Pi Runner → Gateway → 客户端/渠道 完整事件流追踪

1. Gateway 发送的事件类型

SSE Event Type: chat

delta 流式文本增量 content: [{type:"text", text}]，累积式
final 最终完整文本 完成时的完整消息 + stopReason
error 运行错误 errorMessage 字段
aborted 用户取消 流式中断

SSE Event Type: agent

tool 工具调用 phase: start → update → result | name, args, result
lifecycle 生命周期 phase: start → end/error | startedAt, endedAt, model, usage
thinking 推理过程 text, delta（需 reasoningLevel: "stream"）
error 序列间隙 seq gap 检测

不在 SSE 中的事件

  • approval 审批请求 — 基于 Promise 的请求/响应模式，不通过事件流
  • subagent 子 Agent 生命周期 — 仅 REST 轮询（/api/deck/subagents），无实时推送

4. 核心矛盾

矛盾 1: verboseLevel 控制了两件不该耦合的事

  • WS 事件丰富度: Deck 需要 tool result 内容来渲染 BashResultView/DiffPreview → 需要 verbose=full
  • 渠道消息详细度: WeCom 用户只想看最终回答 → 需要 verbose=off
  • 两者共用同一个 session 级配置 → 无法同时满足

矛盾 2: 渠道没有过滤能力

  • WeCom/Telegram 收到什么就发什么 — 没有客户端侧过滤
  • lifecycle 和 thinking 事件始终发送到渠道（不受 verbose 控制）
  • 如果用户配置 verbose="on" 想让 Deck 看到工具，WeCom 也会收到工具日志 → 群里消息爆炸

矛盾 3: 全局广播 hack 不可持续

  • Enhanced fork 的 "全局广播走全量" 是临时方案
  • 如果将来有第二个 backend 客户端不需要 tool result → 无法区分
  • 需要正式的 per-client capability 驱动的事件分发
